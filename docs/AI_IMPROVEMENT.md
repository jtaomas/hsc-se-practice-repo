# Post-exam improvement coach

The post-exam coach gives an evidence-linked learning plan for one submitted paper. It is a separate, bounded LLM workflow after question marking. It cannot change question marks, self marks, exam totals, marking criteria or the original feedback.

## Evidence and trust boundary

`POST /api/improve` requires the same authenticated private-storage session as marking. Its request is exactly:

```json
{"bankId":"1","answers":[{"questionNumber":1,"partIndex":0,"answer":2},{"questionNumber":18,"partIndex":0,"answer":"The submitted response","markingReference":"optional 64-character current marking digest"}]}
```

The illustration above omits other parts for readability; a real request must contain **every** canonical paper part exactly once, including blanks. IDs are one-based question numbers and zero-based part indices. A blank may be `null`; nonblank text, table cells, diagram scenes and closed selections use the existing saved-answer shapes. The endpoint accepts no caller-supplied marks, criteria, feedback, quality ratings or coaching instructions. Submitted-state UI gating belongs to the browser; this API validates a complete answer snapshot, not a server-certified exam sitting or time limit.

The server loads committed banks and computes closed-question scores independently, using the same formulas as the browser. Open-response marks and feedback are read only from that account's private cache under the **current** question, rubric, model, harness and answer digest. Self-assessed marks and legacy client feedback do not become coach evidence. Missing, stale, invalid or unavailable marks stay unknown. Blank answers are distinguished from unconfirmed marks and receive the established zero/no-response treatment.

Diagram cache references additionally require the server-recorded `answerDigest`, which binds the canonical question and sanitized scene while excluding its PNG encoding. A client cannot reuse a diagram reference for an altered scene. The original image/scene assessment remains the marker's responsibility; the coach has the confirmed feedback and scene evidence, not a fresh visual marking task. Canonical inline SVG context is retained as inert data. Closed-question context retains tick-grid column labels, dropdown sentence templates and ordering-task fixed lines/indentation, so a correct score is not accompanied by an ambiguous account of what was selected. Unavailable external image pixels are explicitly identified and must not be inferred.

Cached marks first pass the marker's shared confirmed-provenance validator: current model/harness, both agreeing scoring cores, completed model calls, full auditor approval, eligible selected feedback and the selected-output checksum must all agree. Cached feedback diagnostics are then checked again with the shared feedback-policy validator before aggregation. Criterion and quality quotes remain tied to the original student response. Preparation reads use six workers, existing bounded storage operations and a 45-second overall deadline. Cancellation stops workers from scheduling further reads; already-started reads finish under their storage deadlines. Eligible evidence is never truncated to fit a model request. Detailed source text for blank and unconfirmed parts is deliberately withheld from the model: their IDs, types, statuses, marks and coverage remain visible, but that content cannot substantiate diagnoses. The coach and auditor receive the same evidence projection.

## Deterministic aggregation

The LLM cannot set or rewrite these fields:

- `coverage`: total and confirmed parts, blanks, parts requiring review, other unmarked parts, known score, assessed possible marks, pending possible marks and paper maximum. Confirmed parts include blanks and canonical closed scores.
- `lossSummary`: total known lost marks, exact category totals, counts of parts with a holistic contributing cause, unallocated lost marks and pending possible marks.
- `quality`: each factor's unweighted arithmetic mean across applicable confirmed, nonblank response ratings, rounded to one decimal; number of contributing responses and their part IDs. Insufficient or inapplicable evidence is `null`, never an invented zero.

The browser keeps these verified aggregate ratings visible when the narrative plan needs review. It identifies the unconfirmed explanation and does not display an unapproved practice plan.

The nine categories are knowledge gap, technical error, missing requirement, insufficient explanation, application gap, unsupported judgement, misread command, communication and no response. Exact additive allocations are summed directly from the validated marker output. A holistic rubric's lost marks cannot be assigned numerical causal weights: those marks remain `unallocatedLost`, while category occurrences are counted once per part. Closed errors are also unallocated by cause because a wrong selection does not establish why it was chosen. Blank losses are exact no-response losses. **Do not add holistic occurrence counts to exact category marks.**

The 11 quality factors are clarity, concision, technical accuracy, relevance, structure, reasoning, evidence/examples, terminology, consistency, code quality and diagram quality. They are contextual response diagnostics, separate from rubric marks. Code or diagram evidence does not justify prose-style diagnoses. A one-response mean is explicitly supported by only one response; these ratings are not psychometrically calibrated measures of a student's ability.

## Two-call harness

`server/improvement-engine.js` makes one coach call and then an independent audit call using `deepseek-flash`, thinking enabled and low reasoning effort. This controls a completion failure observed with high effort and a 16,384-token cap; it does not change any schema, evidence or independent-audit gate. Each request has no tools or function definitions, and no submitted code executes. The coach receives the canonical evidence and validated feedback. The auditor receives that same original evidence and the complete proposed plan, independently checks it, and may only approve or veto.

The coach must produce:

1. A paper-specific synthesis and supported strengths.
2. Likely knowledge points to review, distinguishing possible review needs from demonstrated misconceptions.
3. Writing observations, such as repeated statements, dense clauses, weak causal links, poor signposting or imprecise terminology, only when evidenced.
4. Detailed feedback and an actionable next step for each quality factor, including honest explanations for null ratings.
5. Up to three prioritized practice actions, each with evidence links, concrete steps, an exercise, observable success checks and a flexible practice sequence.
6. Specific limitations and uncertainty.

Every observation cites exact evidence by `partId` (for example `18.0`), source and quote. For confirmed nonblank parts, the model also receives `objectiveReferences`: server-generated handles such as `@objective:23.0:1` paired with exact nonempty objective lines of at most 400 characters. A model may place one such handle in an objective evidence quote, or continue using a literal quotation. Handle IDs include the part ID and are looked up only in that cited part with source `objective`; unknown, foreign, concatenated or wrong-source handles are rejected. Known handles are resolved once to immutable original lines before the same exact-substring validator and independent auditor run. The persisted public plan contains original quotations, not generated handles. Long objective lines and all other source text remain unchanged and support exact literal excerpts; the catalog does not truncate evidence. Its request overhead is covered by the existing byte limit. Blank and unconfirmed parts receive no catalog. Sources are `answer`, `feedback`, `criterion` and `objective`. A criterion alone cannot establish a student weakness. A recurring observation requires at least **two distinct assessed parts** supporting the same claim; duplicate quotations from one part do not suffice. Isolated observations must remain limited to that response. Writing patterns require nonblank prose responses. Blank responses cannot establish knowledge gaps. Unconfirmed answers cannot supply diagnostic evidence. Neither model may infer personality, disability, motivation, mental health or long-term habits.

All output is strict JSON, including rejection of duplicate keys. The deterministic validator enforces exact keys, length bounds, factor coverage, allowed evidence references, literal quotations, recurrence counts, applicability and sequential priorities. The auditor also checks meaning: citation relevance, unsupported certainty, generic/circular advice, preservation of marks, separation of optional style advice and concrete practice checks. All 11 positively worded audit conditions must return `pass`; `fail` and `uncertain` both veto release. Each failed or uncertain condition must have exactly one issue, while passing conditions have no issue. The shared `assessment-audit` validator rejects booleans, missing checks, contradictory issues and extra keys. Stored successful audits retain only the check outcomes and zero issue count. A mismatched model identity, incomplete completion, refusal, unexpected tool call, invalid schema, evidence failure or auditor veto returns `needs_review`, with no unconfirmed narrative plan. Deterministic coverage and aggregates remain available. Marks never change.

The auditor is a separate call, **not a different independent model family**. Correlated errors are still possible, and syntactic checks cannot prove that a quoted sentence supports a semantic claim. A teacher can review the linked evidence and suggested plan.

## Budgets, persistence and privacy

The model allowance is 24,576 output tokens for the coach and 16,384 for the auditor, with 115 seconds for the coach, 105 seconds for the auditor and a 225-second overall model deadline. Both retain low reasoning effort. A complete evaluation reserves 40,960 output tokens before starting. The browser allows 295 seconds, while the deployment retains its 300-second function guard; canonical evidence preparation has a separate 45-second deadline, and authentication/storage also need time. These bounds do not guarantee completion under all provider or storage conditions. Request bodies are capped at 800,000 bytes; response streams at 600,000 bytes; returned plan at 58,000 bytes. Timeouts race both network operations and body reading, so a provider ignoring abort cannot keep the request pending indefinitely. No retries or automatic LLM repair loops multiply cost.

The endpoint uses the marking store's existing per-account and site-wide daily paid-job quota and distributed lease. A domain-separated digest includes the current evidence, model and coaching harness version. Coaching therefore cannot bypass quota through a second endpoint. A successful plan costs two calls; a failed paid reservation still consumes its quota slot. All-blank or otherwise insufficient confirmed evidence produces a deterministic explanation without a paid reservation.

A stored plan uses an internal wrapper with `mark:null`, `improvement:<validated plan>`, and completion status `marked` or `needs_review`; this status describes job completion and is not a question grade. The API unwraps the plan into `ready` or `needs_review`. Cached plans work when the provider key is unavailable. Every cached plan is revalidated against the current canonical evidence: inner and outer provenance, exactly two completed calls in coach/auditor order, matching requested and returned model identities, successful finish reasons, current reasoning effort and per-stage token cap, positive audit approval, coverage, loss totals, ratings, supporting part IDs and literal quotations must still match. Contradictory failure metadata invalidates a ready plan. The same validation also runs before saving a new result. The shared coaching version is `post-exam-coach-v10`. Version 2 introduced cache revalidation; version 3 changes reasoning effort and removes unusable blank/unconfirmed source details from model context; version 4 adds readable closed evidence and checks for distinct findings and technically appropriate practice; version 5 migrates to positive audit outcomes, clarifies coverage and tightens closed-answer inference and cache provenance; version 6 separates stage token caps, modestly extends the audit deadline, limits developed priorities to three and adds bounded validation diagnostics without weakening factor-evidence checks; version 7 clarifies that the model returns only quality commentary and references, while the server reattaches numerical aggregates; version 8 adds optional objective-line citation handles resolved to original text before the existing validation and audit; version 9 adds explicit accuracy controls for claimed security effects and optional integrity explanations; version 10 distinguishes tentative topic-review suggestions from unobserved causal claims and requires full-credit-only priorities to be explicitly optional. Each version invalidates earlier plans. A newly confirmed mark, answer change, question/rubric revision or harness change changes the digest and invalidates the old plan. A canonical SHA-256 checksum of the ready plan's public payload (excluding audit metadata) binds the stored approval to its exact summary, findings, quality commentary and practice actions. Object keys are sorted and arrays retain order, so JSON roundtrips do not invalidate it. Cache reads require the checksum to match as well as the semantic structure and evidence checks. This detects accidental content changes; it is not a signature and cannot authenticate against a party able to replace both payload and checksum. Results are returned only after private persistence succeeds.

Questions, submitted answers and confirmed feedback are sent to the configured provider to create and audit the plan. Private cache records remain scoped to the authenticated account. Returned plans contain short evidence quotations, so they remain educational records and should be handled like the original feedback. Provider response internals and credentials are not exposed as user errors.

## Explicit live coaching smoke evaluation

`scripts/evaluate-improvement.js` uses the provider directly through the bounded coach engine. It never calls production `/api/auth`, `/api/mark` or `/api/improve`, and it never writes an account. It requires a prior **live** marking report and the exact fixture snapshot whose digest appears in that report. A mismatched fixture digest, changed canonical question/rubric, different marking harness/model, invalid result evidence or incomplete marking audit causes rejection before any coach request. Preserve fixture snapshots when extending the calibration corpus.

For each part in the chosen bank, selection is the first confirmed, nonblank, current-version live trial in source-report order. Selection does not use expected marks, ranges, tags, rationales or agreement with labels. Only the selected actual marker result is put into a temporary in-memory private-store adapter; the only added fields are recomputed canonical provenance hashes. `improvement-input` validates those records through the same path as the application. The provider's marks, feedback, losses and ratings are not invented or changed. The same shared marker-provenance helper used by the application checks each selected live result, including its selected-feedback identity and output checksum. Fixture labels and source-report comparison metrics never enter either model prompt.

The evaluator builds a complete controlled synthetic attempt: selected open responses come from that report; other open parts are deliberate blanks; successive closed parts rotate between a canonical correct selection, a deterministically changed selection and a blank. The real server scorer computes closed marks. Both the prompt and report identify this as a synthetic composition, not a real student's exam. A single accepted written part cannot support recurring writing-pattern claims. The plan and its limitations must respect this limited evidence.

First produce a fresh report with the **current installed marking harness** and current 105-case fixture using the opt-in direct-engine command in [the marking calibration guide](MARKING_CALIBRATION.md#opt-in-to-a-paid-direct-engine-comparison), setting `--output ../review-artifacts/marking-current-live.json`. Keep the default `tests/fixtures/marking-calibration.json` fixture, and include cases from the bank being coached. At least one nonblank case for that bank must receive a confirmed live mark. An earlier smoke report from a different harness cannot be reused merely by renaming it; run the current marker again or use an already-produced matching current-harness report.

After that report exists, offline coaching-input validation is the default and needs no credential:

```sh
node scripts/evaluate-improvement.js --validate \
  --fixture tests/fixtures/marking-calibration.json \
  --marking-report ../review-artifacts/marking-current-live.json \
  --bank 1 --output ../review-artifacts/coach-input-validation.json
```

Live execution additionally requires `--live`, explicit `--max-calls`, `--max-output-tokens`, `--max-usd`, and both `--input-usd-per-million` / `--output-usd-per-million` using verified current prices. The hard ceilings are 6 calls, 98,304 reserved output tokens, $2 estimated reservation and 3 repetitions. A default one-repetition run needs at most two calls and reserves 40,960 output tokens. The existing 98,304-token hard ceiling permits at most two complete repetitions under the current stage caps; if three are requested, the evaluator stops before starting a third without enough remaining reservation. `--env-file .env.eval` reads only `DEEPSEEK_API_KEY` without executing the file. No credential is printed or stored in a report. Output paths cannot equal an input or the environment file.

Dollar reservations use conservative UTF-8 request-size estimates plus the complete output-token allowance. This is a budget guard under the supplied prices, not a verification of the actual bill. Reports retain source/fixture/input hashes, the chosen report trial indices and unchanged actual marks, controlled-part treatments, coverage, complete coaching output, returned-model audit metadata, reported token counts and estimated usage. Failed or missing usage is reported as incomplete, not zero cost. Reports are written with owner-only permissions and checkpoint after each repetition. Tests use fake provider responses to verify no label/secret leakage and enforcement of all three budgets; those tests do not perform paid calls.


## Live completion failure and version 3 correction

A version 2 smoke evaluation on 24 October 2026 exhausted exactly 16,384 completion tokens after about 87 seconds and returned `finish_reason: length`. No completed plan or quality judgement was released; the independent auditor was not called. That report did not retain the provider's reasoning-token breakdown, so the precise reasoning-versus-final-output split is unknown. A failed completion cannot be described as useful coaching evidence.

Version 3 keeps the same 16,384-token per-call limit, two-call workflow, timeouts, strict validation and audit veto. Both calls use the provider's supported `low` effort level, and blank/unconfirmed source text is removed because it is ineligible for diagnosis; statuses and deterministic totals remain intact. All confirmed nonblank answers, question context and feedback are preserved. The prompt asks for developed exercises and observable success checks without padding list limits. There is no automatic retry or budget increase. Whether the lower effort maintains semantic quality must be checked against returned plans; deterministic validation alone cannot establish this.

The provider documents `low`, `high` and `max` thinking effort; `medium` maps to `high`, so changing to `medium` would not solve an excessive-deliberation problem. The completion response can report reasoning tokens separately and signals truncated output with `finish_reason: length`. See the official [thinking-mode controls](https://api-docs.deepseek.com/guides/thinking_mode/) and [chat-completion API](https://api-docs.deepseek.com/api/create-chat-completion/). Version 3 records requested effort, per-call cap, reasoning-token counts when supplied, final-content byte counts and source/projected evidence sizes. It never retains or redisplays provider reasoning text. Missing reasoning usage is reported as unknown, not zero.


## Independent review of the version 3 plan

The version 3 bank 1 smoke run completed both calls and passed its audit, but independent review found substantive coaching weaknesses: three writing findings repeated the same undeveloped salting explanation; the leading action treated deliberately generated blanks as a completion-practice priority; a universal writing exercise imposed connector/terminology quotas even where the question might only ask for a name; and a backward-loop success check incorrectly assumed every neighbouring value had already been updated. Some closed-choice strengths also inferred reasoning that the selection itself did not demonstrate. The useful elements were accurate salting repair, scenario-transfer practice, evidence links and unchanged marks/ratings. An audit pass therefore did not establish uniformly good coaching.

Version 4 groups one underlying cause into one finding, limits the plan to five developed priorities, adapts practice to question commands, separates synthetic blank controls from real omissions and requires equivalent meaning rather than exact phrase quotas. Two explicit auditor flags cover technical correctness of new practice and distinct/proportionate findings. Closed responses now supply readable canonical selection/comparison text for literal citations instead of raw indices and JSON snippets; scoring formulas and private-source binding are unchanged. Both calls retain low reasoning effort, the 16,384-token cap and the same evidence and timeout gates. These changes still need a measured live probe and independent review; tests only establish the new mechanical checks and refusal paths.

## Observed version 5 bank 1 plan and two-response pattern evidence

The version 5 bank 1 run completed with a ready plan after two calls in about 105.6 seconds, using 19,126 reported completion tokens, of which 14,819 were reported reasoning tokens. Its source was an actual version 5 full-credit hashing/salting response plus controlled closed choices and blanks. Independent reconstruction from the frozen source report confirmed unchanged score coverage, loss aggregates, factor ratings and the public-payload checksum. This source answer was concise; unlike the version 4 probe, it did not contain repetition, so the runs are not a controlled comparison of the same input.

The explicit claim that a correct choice was not a guess did not recur. The CSS explanation no longer called the directly applied font-size declaration inherited. The previous earned-versus-assessed denominator claim was absent, and the requirements exercise asked for additional measurable requirements without replacing the function. The plan had four distinct practice priorities, useful delayed-retrieval and transfer tasks, no synthetic-blank completion intervention, and no writing-pattern claim from the one short prose response. Its descending array-trace practice correctly asks students to account for neighbours updated in the changed loop order.

Some limitations remain. The title “Applies CSS cascade and specificity” attributes a skill more strongly than the directly observed correct selection, although the detail discusses that selection. One exercise first specifies four table columns (“control, mechanism, attack blocked, one-sentence explanation”) and then asks to add a “fourth column” for an attack the control does not stop; this should be a fifth column. Several classification counts also vary between the steps, exercise and later check, making the practice less tidy than its audit implies.

The summary says: “Many parts are blank; these are treated as unknown, not as evidence of missing knowledge, and no time-management or attempt-all conclusion is drawn.” In context this concerns diagnostic evidence, and null code/diagram ratings similarly concern unassessable quality. It does not explicitly claim that blank marks are pending; the deterministic coverage correctly reports no pending possible marks and includes the blank zeroes. Still, “knowledge or quality cannot be inferred from blanks” would communicate that distinction more clearly than calling the blanks unknown. This is a wording limitation rather than a demonstrated changed-score error. All 11 positive audit conditions passed despite the above semantic and instructional shortcomings.

A separate two-case pattern fixture retained the existing bank 7 question 14 and question 27 full-credit content while repeating the short answer three times and repeating the essay's substantive Proposal A paragraph twice more. The canonical source hashes were unchanged. Both labels were written and independently reviewed before paid evaluation: 3/3 for question 14 and preferred 8/8 for question 27, retaining the original 7–8 holistic band ambiguity for reasons unrelated to repetition. The frozen 105-case marking corpus was not modified.

The version 5 marker confirmed **3/3 and 8/8**, with no lost-mark items, and assigned concision **2/10 and 3/10**. Both results cite literal duplicated content in distinct prose parts; the coach input validator accepts their actual provenance and produces a concision mean of **2.5/10** over those two parts. This supplies appropriate evidence for testing one recurring repetition finding within a synthetic paper and optional editing at full marks. These marker results alone do not establish that the coach will produce that finding correctly; the separate coaching output must be reviewed.

The source feedback itself also needs human scrutiny. Question 14's optional advice refers to “how hashes verify integrity” and a “hash/MAC of the message”, without distinguishing an ordinary hash from authenticated integrity protection; these should not be presented as interchangeable security mechanisms. Its reasoning commentary also associates “so an interceptor cannot read it” with authentication as well as encryption, although that phrase supports confidentiality. The coach must not turn optional extensions into missing knowledge or additional full-mark requirements.

## Captured version 6 schema failure and version 7 format clarification

The version 6 pattern attempt finished its draft normally after about 69.2 seconds, using 12,000 completion tokens, including 7,901 reasoning tokens. It returned `needs_review` before the auditor because the quality rows had extra fields. The new bounded diagnostic identified `clarity`, `quality[0].fields`, `extra_fields`, and the separately retained final-only draft confirmed the exact cause: every quality row copied a `rating` field from the source. The copied means were correct, including concision 2.5 and null code/diagram ratings, and there were no other extra fields. The validator nevertheless correctly rejected them instead of stripping or accepting model-supplied numeric metrics. The original version 6 report remains preserved.

The prompt had told the coach to use source quality exactly as provided while separately specifying an output shape without numeric ratings. Version 7 removes that ambiguity. Source metrics are explicitly read-only; model quality rows must contain only `id`, `feedback`, `action` and `evidencePartIds`. The server reattaches unchanged `rating` and `assessedParts` after validation. Compact format-only examples illustrate an assessed factor and an unassessable factor, followed by a final exact-key check. The model is also explicitly told not to return top-level `coverage` or `lossSummary`.

The schema, allowed evidence references, all 11 factors, independent audit, token caps, deadlines and three-priority limit are unchanged. New regression cases show that copied ratings are rejected even when numerically correct, including nulls; copied assessed-part counts and aggregate objects are also rejected. No output-stripping or automatic repair path was added. This captured cause explains the version 6 failure; the uncaptured first version 5 `quality_evidence` failure cannot be assigned the same cause with certainty. Version 7 still requires its own live result and independent assessment of the resulting teaching plan.


## Version 7 literal-citation failure and version 8 objective handles

The version 7 pattern run completed its draft normally in about 65.9 seconds, using 11,481 completion tokens, including 6,054 reasoning tokens. Every quality row now had exactly the four requested fields, so the measured copied-rating failure did not recur in this run. The plan was nevertheless withheld before audit with `coach_evidence`.

Final-only capture identified one failing quotation: a strength about part 23.0 quoted three correct dropdown results as a single sentence separated by spaces, while the authoritative objective text separates those same lines with newlines.
